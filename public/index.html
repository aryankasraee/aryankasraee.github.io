    03 / data · PostgreSQL, MongoDB, Valkey

    Kill the primary database. Count what gets lost.

    This replays the failover drill from my Patroni lab: the main database dies while an app is writing to it. Watch how long writes stop, and whether any confirmed write disappears.

    17.0s without writes
    17.0 s · 0 writes lost

      In plain terms: the main database died, saving paused for 17 seconds, then a standby took over and not one saved record was lost.

      Lab replay at 3× speed. Measured run: largest gap between two acknowledged writes 17,045 ms; 0 acknowledged writes lost; old primary rejoined as a replica.

      • prodPatroni PostgreSQL, MongoDB replica sets and Valkey with Sentinel at Classeh: failovers, replica rebuilds, backups.
      • labWhy 17 s: nobody is promoted until the dead leader's lock expires (ttl 15 s) and HAProxy notices (2 × 1 s checks). Why 0 lost: synchronous replication acknowledges a commit only once a standby has it.
      LearnedThe first restore from backup failed: Patroni writes absolute paths into postgresql.conf. You only find that out by restoring.

      Incident · 5–6 Oct 2026 · my own monitoring stack
      1. 20:24 UTCHost load jumps to 12 right after deploy. cAdvisor hit its 256 MB limit and was swapping; disk I/O at 100%.
      2. 20:27 UTCFixed: every container gets memory_swap = memory; cAdvisor's disk metric disabled. Load back under 1.
      3. 20:31 UTCGrafana 13 tries to update its own Prometheus and Loki plugins. The plugin CDN answers 403 to Iranian IPs and leaves them unregistered: every dashboard silently shows "No data".
      4. 06:50 UTCFound from a screenshot, fixed by disabling plugin auto-install. Prometheus kept every sample, so no data was lost.
      5. afterI now verify dashboards through Grafana's own query API, not only against Prometheus.
